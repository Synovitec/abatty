# i18n: best practices

Reference guide for organising translation files that stay maintainable beyond a few thousand lines. The examples use Next.js App Router / next-intl, with the react-i18next equivalents. Official sources at the end.

---

## 1. Is a 7,000-line file a problem?

Not in itself. Three questions, in this order.

**Does this JSON go to the browser?**
That is the only point with a real cost. If everything is rendered server-side, the messages never leave the server and the file's weight does not matter. The next-intl docs are explicit: with server-side i18n there is no need to split messages by route or by component.

**Are you losing the overview?**
The i18next docs give the commonly accepted threshold: beyond about 300 segments in one file, you start losing the thread. At 7,000 lines you are far above it. That is the real reason to split, before performance.

**Does the file create git conflicts?**
A single file touched by every branch produces systematic conflicts on translations. Splitting by domain settles that.

In short: not a technical problem, an ergonomics and client-payload problem.

---

## 2. Splitting into namespaces

### The rule

Split **by functional domain or by feature**, never by component. That axis is stable over time and survives interface refactors, unlike a split that mirrors the file tree.

```
messages/
  fr/
    common.json       # nav, footer, generic buttons (save, cancel)
    validation.json   # every validation message
    glossary.json     # business terms to translate consistently
    home.json
    booking.json
    account.json
    admin.json
  en/
    ...
```

`common.json`, `validation.json` and `glossary.json` are the three cross-cutting namespaces the i18next docs recommend. The rest follows the features.

### Governing `common`

It is the namespace that rots first. Explicit rule: `common` accepts only what is genuinely universal and semantically stable (months, countries, a dialog's "Cancel"). Everything else belongs to a domain. If `common` exceeds 200 to 300 keys, a domain has crept in.

### When not to split

Small project, everything in Server Components, one developer. A single file is perfectly valid. Split when the pain arrives, not before.

## 3. Key naming

### The three schools

| Approach              | Example                        | Verdict                                                                    |
| --------------------- | ------------------------------ | -------------------------------------------------------------------------- |
| Structured (semantic) | `booking.form.pickupDate`      | **Recommended by default**                                                 |
| Natural language      | `t('Please enter your email')` | Avoid: fixing a typo changes the key and breaks every existing translation |
| Generated             | `t('key_aB38fG1p')`            | Viable only with a TMS and an IDE extension that shows the source text     |

A key is a contract between three parties: the developer (a predictable interface), the translator (the key is often their only context), and the TMS (the key is the immutable ID that carries history, screenshots and comments). Renaming a key breaks that contract and restarts the chain from zero.

### Conventions

- **Casing**: `camelCase` or `snake_case`, but one, decided and documented. `snake_case` aligns with i18next's plural format.
- **Depth**: 2 to 3 levels maximum. `checkout.paymentForm.submitButton` is the upper limit.
- **Shape**: `object.action` or `section.element.action`.
- **No abbreviations**, no name that describes the text rather than the role.

```json
{
  "booking": {
    "form": {
      "pickupDate": "Pick-up date",
      "submit": "Book"
    },
    "status": {
      "pending": "Pending",
      "confirmed": "Confirmed"
    }
  }
}
```

Bad: `"book_now": "Book now"`. The day the text changes, the key lies.

### Naming interpolation variables

Same conventions as keys. A variable must describe the injected value: `{{year}}`, `{{customerName}}`, not `{{v1}}`.

## 4. Do not reuse keys

Counter-intuitive for a developer trained on DRY, but it is the field's established rule: **one unique key per string instance in the interface**. Textual identity is not semantic identity.

Three reasons:

- **Grammatical context**: "Read" the verb and "Read" the status do not translate the same way. A shared key forces them to be identical.
- **Business context**: "Cancel" a subscription and "Cancel" a dialog do not carry the same weight.
- **Future divergence**: two identical "Back" buttons today, one of which becomes "Previous step" next month. A shared key makes the change impossible without breaking the other.

`userProfile.buttons.save` and `documentEditor.buttons.save` beat a shared `common.save`.

Exception: the strictly governed `common` namespace (months, countries, units).

If a label must stay rigorously identical everywhere for product reasons, extract a hook rather than share the key, as recommended in the next-intl repository discussions.

## 5. ICU MessageFormat

The field's standard, used natively by next-intl. It embeds the logic in the string, which lets the translator drive it.

### Plurals

```json
{
  "results": "{count, plural, =0 {No vehicles} one {# vehicle} other {# vehicles}}",
  "unread": "{count, plural, =0 {No new messages} one {One new message} other {# new messages}}"
}
```

A `count > 1 ? 's' : ''` in JavaScript breaks on the first language with three forms (Russian) or six (Arabic). The library knows the CLDR rules; your code does not. The `other` category is the only one guaranteed in every locale: always define it.

### Select

```json
{
  "likedPost": "{gender, select, female {She liked your post.} male {He liked your post.} other {They liked your post.}}"
}
```

### Interpolation: use sparingly

An important and often ignored point, documented explicitly by i18next. Interpolation concatenates fragments, and a sentence built at runtime is hard, sometimes impossible, to translate correctly without multilingual grammar rules.

The canonical example:

```json
{ "fees": "All fees will be charged to {{paymentType}} registered on this account." }
```

In German, the article preceding `{{paymentType}}` changes with the injected value. The result produces grammatically wrong sentences half the time.

**Rule**: interpolate only values known at runtime (timestamps, user input, API data). When the possible values are known in advance, write complete, self-contained strings:

```json
{
  "feesCreditCard": "All fees will be charged to the credit card registered on this account.",
  "feesPaypal": "All fees will be charged to the PayPal account registered on this account."
}
```

## 6. Rich text and HTML

Never raw HTML in translations rendered through `dangerouslySetInnerHTML`. A security risk and a loss of control over element behaviour.

**next-intl**: `t.rich()` with the tags passed as parameters.

```tsx
t.rich("terms", {
  link: (chunks) => <Link href="/terms">{chunks}</Link>,
});
```

```json
{ "terms": "Please accept our <link>terms and conditions</link>." }
```

**react-i18next**: the `<Trans>` component.

```tsx
<Trans i18nKey="terms.agreement">
  Please accept our <Link to="/terms">terms and conditions</Link>.
</Trans>
```

The translator can reorder the sentence; you keep control of the component.

For long content (legal notices, terms), leave JSON: localised MDX files (`content.fr.mdx`, `content.en.mdx`) or a CMS with a portable format. That is the alternative the author of next-intl recommends to replace `t.raw`.

---

## 7. Dates, numbers, currencies

Never in translation files. Always the native `Intl` APIs with the active locale, through the library's formatter.

```tsx
const format = useFormatter();
format.dateTime(date, "short");
format.number(price, { style: "currency", currency: "EUR" });
```

Inline in ICU when needed:

```json
{ "priceFrom": "From {price, number, ::currency/EUR}" }
```

---

## 8. What must not be in the JSON

- Raw HTML (see section 6)
- URLs and slugs: dedicated routing configuration
- Business data: country lists, currencies, time zones (API or package, `Intl.DisplayNames`)
- Hard-formatted dates and numbers
- Arrays of messages: prefer individual, statically analysable keys

## 9. next-intl specifics (App Router)

### Server-first

The official order of preference for Client Components, from most to least performant:

1. Pass already-translated labels as props or children from a Server Component
2. Lift the state server-side (search params, cookies, DB)
3. Provide the selected messages via `NextIntlClientProvider`
4. Provide all messages (the default behaviour)

Case 1 is the target. Cases 3 and 4 are what bloats the payload.

### Limiting the client payload

By default next-intl sends every message to the client. To cut that:

```tsx
<NextIntlClientProvider messages={null}>...</NextIntlClientProvider>
```

Then, locally, provide only what is needed:

```tsx
import pick from "lodash/pick";
import { NextIntlClientProvider, useMessages } from "next-intl";

export default function Counter() {
  const messages = useMessages();

  return (
    <NextIntlClientProvider messages={pick(messages, "ClientCounter")}>
      <ClientCounter />
    </NextIntlClientProvider>
  );
}
```

Automatic tree-shaking of messages is still under study on the next-intl side; selection remains manual today.

### ICU precompilation (a big gain, one flag)

Since `next-intl@4.8`, build-time precompilation removes the ICU parser from the runtime. Announced gain: about 9 KB compressed less on the server and client bundles, the total cost of a client-side translation falling to around 4 KB, with a formatting runtime of about 650 bytes. Formatting also becomes noticeably faster.

```ts
// next.config.ts
import createNextIntlPlugin from "next-intl/plugin";

const withNextIntl = createNextIntlPlugin({
  experimental: {
    messages: {
      path: "./messages",
      format: "json",
      precompile: true,
    },
  },
});

export default withNextIntl();
```

Limit: `t.raw` is not supported with precompilation. Still marked experimental.

It is the most direct answer to a large volume of messages: rather than splitting everything, precompile.

### Strict typing

Module augmentation via `AppConfig` (next-intl v4+):

```ts
// global.ts
import { routing } from "@/i18n/routing";
import { formats } from "@/i18n/request";
import messages from "./messages/fr.json";

declare module "next-intl" {
  interface AppConfig {
    Locale: (typeof routing.locales)[number];
    Messages: typeof messages;
    Formats: typeof formats;
  }
}
```

With several namespaces:

```ts
type Messages = {
  common: typeof import("./messages/fr/common.json");
  booking: typeof import("./messages/fr/booking.json");
};
```

To also type the **arguments** of messages (not only the keys), enable declaration generation:

```ts
const withNextIntl = createNextIntlPlugin({
  experimental: {
    createMessagesDeclaration: "./messages/fr.json",
  },
});
```

Otherwise TypeScript infers imported JSON values as plain `string`, which prevents checking ICU arguments.

### Catalogue formats

JSON carries only key/value pairs. To carry context (a description for the translator, a source file reference), next-intl supports the **PO** format or a custom codec. That is the real way to give context without a TMS.

## 10. react-i18next / i18next specifics

### Namespaces

```js
i18next.init({
  ns: ["common", "booking", "admin"],
  defaultNS: "booking",
});

// load on demand
i18next.loadNamespaces("checkout");
```

Avoid the `common:myKey` prefix in calls; prefer the `ns` option:

```js
t("button.save", { ns: "common" });
```

Recommended split axes: by view or page, by application section (admin area), by lazy-loaded module.

### Selector API (TypeScript)

The historical weakness of structured keys (readability in code, no autocomplete) is solved:

```ts
t(($) => $.userProfile.labels.firstName);
```

Autocomplete, compile-time checking, safe refactoring.

## 11. Quality and CI

### One source of truth

The default language file is the master. The other languages derive from it. A parity check in CI fails the build if a key exists in the master language and not in another, otherwise the holes are discovered in production. The pre-commit hook refuses a locale file touched without its siblings.

### Linting

For next-intl, the officially recommended tool is `@eloqnt/cli`, which does AST analysis and detects missing translations and inconsistent ICU arguments between locales:

```bash
npm install @eloqnt/cli --save-dev
npx eloqnt lint
```

```ts
// .eloqnt/config.ts
import { defineConfig } from "@eloqnt/cli";

export default defineConfig({
  srcPath: "./src",
  messages: {
    path: "./messages",
    locales: "infer",
    sourceLocale: "fr",
    format: "json",
  },
});
```

Integrable in CI, with optional filling of missing translations. For hardcoded text in JSX, `react/jsx-no-literals` or `eslint-plugin-i18next` (`no-literal-string`) at error.

### Orphan keys

On a file of several thousand lines, expect 15 to 30 % dead keys.

- `i18n-unused`: detection and removal of unused keys
- `i18next-parser`: extraction from the code, moves obsolete keys into an `_old.json` file instead of losing them

Run the audit as a scheduled task, not only by hand.

### Fallback

If a key is missing in a locale, show the master language, never the raw key. In development, make the missing key visible (colour, marker) so it is spotted immediately. The fallback chain ends on English and never on the first customer's language (I18N.2 of the standard); a platform that accepts any ISO 639-1 code will meet an RTL language and writes its layouts in logical properties (`margin-inline-start`, `ms-*`), with a single `dir` on the container.

## 12. Context for translators

A good naming convention is not enough. The translator is a linguistic expert, not a mind reader. The context vacuum remains the first cause of bad translation.

Means, from lightest to most complete:

1. Explicit semantic keys (free, insufficient alone)
2. PO format or a custom codec, which carries descriptions and file references
3. A TMS (Crowdin, Locize, Tolgee, POEditor): in-context editor, screenshots, translation memory, glossary

With i18next and locize, the description can be provided straight from the code when the developer writes the key:

```js
t("userProfile.buttons.requestExport", {
  defaultValue: "Request my data",
  tDescription: "GDPR export request button. Formal tone.",
});
```

The word "Book" alone is untranslatable without knowing whether it is a verb or a noun.

---

## 13. Workflow

- Develop in one language (the master language). The other languages are filled afterwards, never in parallel, otherwise every wording iteration is paid three times.
- Never rename a key lightly: it is a loss of history on the TMS side.
- Set `lang` and `dir` on `<html>` from the locale (accessibility and SEO).
- Generate the static params for every locale and prefer static rendering.
- Measure before optimising. If the Core Web Vitals are good, do not split for the sake of splitting.

## 14. Team checklist

To decide and document once, in the repository's `CODE_CONVENTIONS.md`:

- [ ] Key casing: camelCase or snake_case?
- [ ] Namespace axis: by feature or by domain?
- [ ] Maximum depth: 2 or 3 levels?
- [ ] Reuse policy: unique keys by default?
- [ ] Admission rules for `common`?
- [ ] How does context reach the translator?
- [ ] How are plurals and rich text handled?
- [ ] Who audits orphan keys, and how often?
- [ ] Is key parity checked in CI?
- [ ] Precompilation enabled?
