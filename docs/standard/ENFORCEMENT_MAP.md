# Enforcement map

"Is there a guarantee the agent applies the rules?" has one honest answer: **only where a
machine refuses the work without them.** the agent's own documentation states that
`CLAUDE.md` and skills are context, not enforcement. So the guarantee is built in layers,
and this page says which layer each rule sits in.

## The four levels

| Level       | What it means                                                                                                                 | Who can bypass it                                                                  |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| **Hard**    | A machine refuses: an ESLint error, a HARD metric in the ratchet, a hook denial, a CI step that fails, a permission deny rule | Nobody without editing the check itself, which the reviewer and the `git log` show |
| **Ratchet** | Measured; the count may fall and never rise, with a per-file floor. Existing debt is allowed, a NEW violation is refused      | Nobody, except by raising the baseline in the same commit with a written reason    |
| **Review**  | The `standards-reviewer` agent's checklist item before every phase commit, and a human in the morning                         | The reviewer is a model; a `must` it misses ships                                  |
| **Prose**   | Written in the standard, checked by nothing                                                                                   | Anyone, silently                                                                   |

The night run adds four controls that sit above every rule: the **guard hook** (denies the
dangerous commands before they run), the **git shim** on `PATH` (refuses the same force push and
hook bypass in every other shell, because a guard that lives in one tool's hook is a property of
that tool rather than of the repository), the **stop-gate hook** (the session cannot end while
the gate is red, the session left the tree dirty, the changelog is untouched or the state file is stale), and
**CI on the pushed branch** (re-runs every gate independently of the model). A rule enforced
by the gate is therefore enforced three times: at the stop, at the push, and in CI.

## How to read this map

The level of every row is also data: `npx abatty rules` lists the package's checks with their
level (must, should) and their insurance (hard, ratchet, review, prose), `npx abatty explain
<ID>` opens one with its reason and its finding in the repository. This page is the reasoning
behind those levels; the catalog is what a machine reads.

`ratchet:<metric>` names a metric of the repository's standards script (`npm run standards`).
Metric names follow the reference ratchet named in `ADOPTION_STATUS.md`; a repository maps them to its own script. A row
with two levels means the rule has a hard core and a prose remainder, in that order.

## What the numbers say today

Of the 64 rows above, counted at the level of the BEST implementation among the three
repositories: **46 hard, 6 ratchet, 6 review, 6 prose** on 2026-09-13; FLOW.3 moved from
Review to Hard-at-night on 2026-09-14, which the daytime tally does not count. "Best" is doing work in that
sentence - twelve of the hard rows say "where wired", meaning at least one repository has the
mechanism and others do not yet. Which one has what is the dated table in
`ADOPTION_STATUS.md`, and per repository the answer is its own scoreboard in
`docs/STANDARDS_PROGRESS.md` - the map says what the mechanism IS, the status page says who
has it.

The night run does not change a rule's level. It changes who is refused: the same gate that
refuses a human's push refuses the agent's stop, and the same reviewer checklist runs before
every phase commit rather than when someone remembers. The one exception is FLOW.3, which the
night holds harder than the day, because at night nobody reads the diff before the next step.

## Moving a rule up a level

A prose rule becomes insured the same way every ratchet metric was born:

1. **Write the probe** in `scripts/ci/standards/` - one function, one metric name, findings
   with `path:line`, a `scanned` count.
2. **Write its control cases both ways** in `tests/lint/standards-probe.test.ts`: a synthetic
   violation the probe must report, a clean file it must not, and the regression that motivated
   it. A probe with no failing control case is not added.
3. **Measure and record** - `standards:baseline` writes today's number as the floor with its
   per-file debt. If the number is already 0, add the metric to the HARD set instead.
4. **Prove it live**: reintroduce a violation in a scratch file, run the gate, confirm
   REGRESSED or HARD FAIL naming the file, restore.
5. **Log it** in `STANDARDS_PROGRESS.md` with the number, and update this map's row.

For a rule the linter can state (a function limit, a banned import, an a11y attribute), skip
the probe and set the ESLint rule at `error` with the exemption generated from the baseline's
`debt`; promote to unconditional when the debt is empty. For a rule about a moment (before a
commit, at a stop), it is a hook. For a rule about a run (a suite, a drill), it is a CI step.
