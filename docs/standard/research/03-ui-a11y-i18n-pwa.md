# Research cluster 3: UI, components, accessibility, i18n (2025-2026 practice)

Read against `ops-hub/engineering/ENGINEERING_STANDARD.md` (sections 3 Code rules, 6 Product surface rules, 8 Lessons catalogue, 9 What may differ). Sources are official docs first; a blog is used only from a recognized authority, dated/versioned where it matters.

## Topic 1 - React 19 component architecture

- SHOULD pass props explicitly before reaching for Context; only lift shared data into Context once several distant components need the same thing (react.dev/learn/passing-data-deeply-with-context)
- SHOULD prefer composition - extract a component and pass the specific piece as `children` - over threading a prop through intermediate components that do not use it (react.dev/learn/passing-data-deeply-with-context)
- MUST render Context providers as deep in the tree as possible (wrap only `{children}`, never `<html>`/the whole document), so the framework can still statically optimize the rest of the Server Component tree (nextjs.org/docs/app/getting-started/server-and-client-components)
- SHOULD extract a custom hook when the same `useState`/`useEffect` logic is duplicated across components, or whenever an Effect is written at all - wrapping it names the intent and the data flow (react.dev/learn/reusing-logic-with-custom-hooks)
- MUST NOT extract a hook that calls no Hooks itself (use a plain function, no `use` prefix), and MUST NOT build generic "lifecycle" hooks (`useMount`, `useEffectOnce`) that hide dependency issues from the linter (react.dev/learn/reusing-logic-with-custom-hooks)
- SHOULD accept minor duplication (e.g. a one-line `useState` wrapper) rather than extracting a hook prematurely (react.dev/learn/reusing-logic-with-custom-hooks)
- MUST default every layout and page to a Server Component; use a Client Component only for state, event handlers, lifecycle effects, browser-only APIs or a custom hook that needs them (nextjs.org/docs/app/getting-started/server-and-client-components)
- SHOULD place `'use client'` on the smallest leaf that needs interactivity (a `<Search>` bar), never on the layout or page around it, to keep the client bundle small (nextjs.org/docs/app/getting-started/server-and-client-components)
- MUST pass Server Components into Client Components via `children`/props (the "slot" pattern) rather than importing one into a Client Component's own module graph, which React does not support (nextjs.org/docs/app/getting-started/server-and-client-components)
- MUST guard server-only code (secrets, DB clients) with the `server-only` package so an accidental import from a Client Component fails at build time instead of shipping silently (nextjs.org/docs/app/getting-started/server-and-client-components)
- SHOULD stop reaching for `useMemo`/`useCallback`/`React.memo` by default under the React 19 compiler; add them only when profiling shows a real problem or a value's referential identity is part of an external contract (dev.to/ahmed_mahmoud360/react-compiler-in-2026-what-it-actually-memoizes-and-what-it-doesnt-5ga1)
- MUST still hand-memoize inside a `try/catch` block or against a library that assumes stable references (e.g. older TanStack Table) - the compiler skips code it cannot statically analyze (dev.to/ahmed_mahmoud360/react-compiler-in-2026-what-it-actually-memoizes-and-what-it-doesnt-5ga1)
- MUST key list items with a stable id from the data (or a locally generated `crypto.randomUUID()`), never the array index, unless the list is provably static and will never be reordered, filtered, inserted into or deleted from (react.dev/learn/rendering-lists)
- MUST NOT generate keys during render (e.g. `Math.random()`) - it recreates every item's identity on each render, discarding state and running slower than no key at all (react.dev/learn/rendering-lists)
- SHOULD favor hooks-based colocation over a strict container/presentational split; pull stateful logic into a custom hook and keep the component a thin consumer of its return value (react.dev/learn/reusing-logic-with-custom-hooks)

## Topic 2 - File organization (Next.js App Router and Vite/React SPA)

- SHOULD organize by feature (`src/features/<feature>/{api,components,hooks,types}`) rather than by layer once an app is past trivial size, and enforce a one-way import rule: shared -> features -> app, features never import each other (github.com/alan2207/bulletproof-react, project-structure.md)
- SHOULD keep genuinely shared, cross-feature primitives in one top-level `components/ui` (or `components`) folder importable by any feature and by the app layer (github.com/alan2207/bulletproof-react, project-structure.md)
- MUST enforce the shared -> features -> app import direction with a lint rule (`import/no-restricted-paths`), not convention alone (github.com/alan2207/bulletproof-react, project-structure.md)
- SHOULD use a Next.js route group `(name)` to organize routes by team/section or to give a subset of routes their own layout, without adding a URL segment (nextjs.org/docs/app/api-reference/file-conventions/route-groups)
- MUST NOT let two route groups resolve to the same URL (`(marketing)/about` and `(shop)/about` both becoming `/about`) - Next.js treats this as a build error (nextjs.org/docs/app/api-reference/file-conventions/route-groups)
- SHOULD know navigating between two different route-group ROOT layouts forces a full page reload, not a soft navigation - reserve multiple root layouts for genuinely different app shells (nextjs.org/docs/app/api-reference/file-conventions/route-groups)
- SHOULD use a private folder (`_folderName`) to colocate non-routable UI/lib code inside an App Router segment, as a route-scoped alternative to a top-level `lib/<domain>` (nextjs.org/docs/app/getting-started/project-structure)
- SHOULD colocate tests, styles and hooks next to the component that uses them instead of mirroring the source tree in a parallel `test/` directory - proximity is what makes a missing test obvious (kentcdodds.com/blog/colocation)
- SHOULD resist moving a helper into a shared `utils/` folder the moment it is used twice; keep it near its first caller until a second, unrelated caller needs it, to avoid orphaned "tribal knowledge" utilities (kentcdodds.com/blog/colocation)
- MUST avoid barrel (`index.ts` re-export) files on hot import paths in a Vite or Next.js/Turbopack app - a barrel that touches many modules defeats tree-shaking and can cost tens to hundreds of MB of extra build memory because the bundler keeps every re-exported module live until final tree-shaking (vercel.com/blog/how-we-optimized-package-imports-in-next-js; github.com/alan2207/bulletproof-react)
- SHOULD import directly from the defining file instead of through a large or client/server-boundary-crossing barrel; reserve barrels for small, leaf-level, side-effect-free groups (vercel.com/blog/how-we-optimized-package-imports-in-next-js)
- SHOULD use Next.js's built-in `optimizePackageImports` when a third-party dependency ships an unavoidable barrel, instead of waiting on the upstream package to fix it (vercel.com/blog/how-we-optimized-package-imports-in-next-js)
- MUST name component files consistently with what they export (Pascal or kebab, either is fine) and hooks `use-*`; neither Next.js nor bulletproof-react enforces one casing, but both require the team to pick one and hold it (github.com/alan2207/bulletproof-react; nextjs.org/docs/app/getting-started/project-structure)
- SHOULD pick exactly one of Next.js's three documented layouts - all code outside `app`, all code inside `app`'s root, or split by feature/route inside `app` - and apply it consistently; the framework is deliberately unopinionated between them (nextjs.org/docs/app/getting-started/project-structure)

## Topic 3 - shadcn/ui + Radix + Tailwind CSS 4

- SHOULD vendor shadcn/ui components by copying source via the CLI rather than installing a package - components become plain React + Tailwind files owned and diffed on update, not a version bumped blindly (ui.shadcn.com/docs/theming; devtoolbox.blog/shadcn-cli-v2-tailwind-v4-component-workflow-guide)
- MUST define semantic tokens (`background`, `foreground`, `primary`/`primary-foreground`, `muted`, `accent`, `destructive`, `border`, `input`, `ring`) as CSS variables under `:root` and `.dark`, never a hardcoded hex/oklch value inside a component (ui.shadcn.com/docs/theming)
- SHOULD express colors in OKLCH and expose them to Tailwind CSS 4 through an `@theme inline` block mapping each `--token` to a `--color-token` utility, rather than a `tailwind.config.js` palette (ui.shadcn.com/docs/theming)
- SHOULD derive the full corner-radius scale from one `--radius` base variable so resizing the base updates every component together (ui.shadcn.com/docs/theming)
- SHOULD implement dark mode as a `.dark` class toggle overriding the same token names, not a second parallel set of utility classes (ui.shadcn.com/docs/theming)
- MUST compose class strings with a `cn()` helper (`clsx` + `tailwind-merge`) so a later conflicting utility class correctly wins, instead of string-concatenating classNames (shadcn CLI-generated component convention, per ui.shadcn.com/docs/theming)
- SHOULD use Radix's `asChild`/`Slot` pattern to let a component render as, or merge props onto, a caller-supplied element instead of adding an `as` prop or forking the component - `Slot` merges the child's own event handler so the child's handler still runs (radix-ui.com/primitives/docs/utilities/slot)
- MUST set the accessible name on the element that actually renders when composing with `asChild` - Radix clones props onto the child, so a label set on the wrapper is lost if the child does not receive it (radix-ui.com/primitives/docs/guides/composition)
- SHOULD track vendored/copied UI files with a checksum and fail a gate on unreviewed drift - a "copy, don't depend" model has no version to diff against otherwise, which is also why the shadcn CLI's own update flow is framed as a reviewable diff (ui.shadcn.com/docs/theming)
- SHOULD treat opting out of CSS-variable tokens (`--no-css-variables`) as a one-time, whole-project decision - mixing raw utility classes and token-driven classes in one codebase reintroduces the hardcoded-color problem tokens exist to prevent (ui.shadcn.com/docs/theming)

## Topic 4 - Material UI (v7+)

- SHOULD use the `sx` prop only for one-off, single-instance overrides (padding, margin, color) and use `styled()` for any style reused across more than one instance (mui.com/system/styled; medium.com/ashtech "We're too sx-y for our code")
- SHOULD centralize repeated visual decisions in the theme's `components` key (`styleOverrides`, `variants`) rather than repeating the same `sx` object at every call site (mui.com/material-ui/customization/how-to-customize)
- MUST set `useFlexGap` on `Stack` (or move to CSS `gap` generally) instead of relying on its default sibling-margin selector, which cannot be overridden per child (mui.com/system/react-stack; github.com/mui/material-ui/issues/33754)
- MUST NOT rely on MUI System props (`m`, `p`, `display` as bare props) in new code - they are deprecated for removal; use `sx` instead (mui.com/system/react-stack)
- MUST pair `paginationMode="server"` with `rowCount`, `paginationModel` and `onPaginationModelChange` for a server-paginated DataGrid, and implement server-side filtering/sorting too - server pagination alone still filters/sorts only the current page (mui.com/x/react-data-grid/pagination)
- SHOULD use the DataGrid Data Source API when filtering, sorting and pagination must all be server-driven together, since it wires all three to "server" mode consistently (mui.com/x/react-data-grid/server-side-data)
- SHOULD use `100svh` for content that must fit on first paint with mobile browser chrome visible, and reserve `100dvh` for elements meant to intentionally resize as the chrome shows/hides - `100dvh` is not a safe default for a full-screen hero or modal (thelinuxcode.com/viewport-units-in-css-mastering-vh-vw-and-the-modern-dvhsvhlvh-family-2026)
- SHOULD avoid animating height toward `100dvh` - it recalculates on every browser-chrome show/hide and can jitter; animate with `svh`/`lvh` or a fixed unit instead (thelinuxcode.com/viewport-units-in-css-mastering-vh-vw-and-the-modern-dvhsvhlvh-family-2026)
- SHOULD size touch targets at least 48x48dp (Material) / 44x44pt (Apple HIG) with roughly 8px between adjacent targets on any touch surface - stricter than, and sufficient for, WCAG 2.2's 24x24 CSS px legal minimum (web.dev/articles/accessible-tap-targets; smashingmagazine.com/2023/04/accessible-tap-target-sizes-rage-taps-clicks)

## Topic 5 - Semantic HTML, WCAG 2.2 AA, EU Accessibility Act

- MUST target WCAG 2.2, not 2.1 - it added Focus Not Obscured (Minimum) 2.4.11 AA, Focus Not Obscured (Enhanced) 2.4.12 AAA, Focus Appearance 2.4.13 AAA, Dragging Movements 2.5.7 AA, Target Size (Minimum) 2.5.8 AA, Consistent Help 3.2.6 A, Redundant Entry 3.3.7 A, Accessible Authentication (Minimum) 3.3.8 AA, Accessible Authentication (Enhanced) 3.3.9 AAA (w3.org/WAI/WCAG22/quickref)
- MUST provide real landmarks (header/nav/main/footer/aside) and a heading outline with no skipped level, so a screen-reader user can navigate by region or heading (w3.org/WAI/WCAG22/quickref)
- MUST use the native control first - `<button>` not `<div onClick>`, native `<select>`/`<input>` not a custom widget - and reach for ARIA only when no native element expresses the semantics (w3.org/WAI/WCAG22/quickref)
- MUST give every icon-only control an accessible name, placed on the element a Radix/shadcn component actually renders when composed via `asChild` (radix-ui.com/primitives/docs/guides/composition; w3.org/WAI/WCAG22/quickref)
- MUST keep focus order matching visual/DOM order (2.4.3, A) and keep the focus indicator visible and never obscured by sticky headers or other content (2.4.11, AA) (w3.org/WAI/WCAG22/quickref)
- MUST size every touch/click target at least 24x24 CSS px (2.5.8, AA, new in 2.2) - this is the legal floor and is distinct from, and lower than, the 44pt/48dp platform UX convention a mobile-first surface should still use (w3.org/WAI/WCAG22/quickref; web.dev/articles/accessible-tap-targets)
- MUST meet 4.5:1 contrast for normal text (1.4.3, AA) and 3:1 for large text and for non-text UI components such as borders, icons and focus indicators (1.4.11, AA) - two different thresholds, not one flat number (w3.org/WAI/WCAG22/quickref)
- MUST honor `prefers-reduced-motion` and avoid motion triggered purely by interaction that cannot be turned off (2.3.3) (w3.org/WAI/WCAG22/quickref)
- MUST identify form errors in text tied to the offending field (3.3.1, A), and MUST NOT require re-entry of information already collected in the same process (3.3.7 Redundant Entry, A, new in 2.2) (w3.org/WAI/WCAG22/quickref)
- MUST NOT make a cognitive function test (transcribing a password/OTP from memory with no paste/autofill allowed) the only way to authenticate (3.3.8 Accessible Authentication (Minimum), AA, new in 2.2) - allow pasting a TOTP code and password-manager autofill (w3.org/WAI/WCAG22/quickref)
- MUST give any drag-to-operate control a single-pointer alternative (2.5.7 Dragging Movements, AA, new in 2.2) (w3.org/WAI/WCAG22/quickref)
- SHOULD offer consistent help (a support/contact mechanism at the same relative location) once one page in a set offers it (3.2.6 Consistent Help, A, new in 2.2) (w3.org/WAI/WCAG22/quickref)
- MUST treat the European Accessibility Act (Directive (EU) 2019/882) as enforceable law from 28 June 2025 for any e-commerce service sold to EU consumers regardless of provider location - this squarely covers a consumer-facing storefront; B2B-only software has a genuinely disputed scope in current legal guidance, so an admin console must not be assumed exempt by default (twobirds.com/en/insights/2025/a-guide-to-navigating-the-european-accessibility-act; accessible.org/eaa-ecommerce-services-requirements)
- MUST configure `eslint-plugin-jsx-a11y`'s `settings['jsx-a11y'].components` to map every wrapped primitive (e.g. a shadcn `Button` to `button`) AND set `polymorphicPropName` - without both together the plugin silently reports zero violations on a component library's markup (github.com/jsx-eslint/eslint-plugin-jsx-a11y)
- SHOULD scan the rendered DOM with `@axe-core/playwright`'s `AxeBuilder`, scoping with `.include()`/`.exclude()` and asserting `violations` is empty, including after interactions that reveal new UI such as opening a modal (playwright.dev/docs/accessibility-testing)
- SHOULD keep a manual checklist beside automated axe scans - axe/Lighthouse cannot verify focus order, actual screen-reader announcement text, or colors composited at runtime; a release checklist should include a full keyboard-only pass and a screen-reader spot check (playwright.dev/docs/accessibility-testing; general Deque/axe-core scope-of-coverage guidance)

## Topic 6 - i18n

- SHOULD use next-intl for a Next.js App Router app needing Server Component translations with no hydration cost (`getTranslations()` on the server, `useTranslations()` via `NextIntlClientProvider` on the client) (next-intl.dev/docs/getting-started/app-router)
- SHOULD reach for react-i18next/i18next instead when the same translation layer must also serve a non-Next.js surface (a Vite SPA, a mobile app) - the larger-ecosystem, more universal choice at the cost of native Server Component support (gundogmuseray.medium.com/the-definitive-guide-to-i18n-libraries-for-next-js-react-in-2026)
- MUST express plurals with ICU MessageFormat (`{count, plural, one {# item} other {# items}}`) rather than string concatenation or a manual `count === 1 ? x : y` ternary - CLDR plural rules use up to six categories (zero, one, two, few, many, other) and English's two-category system does not generalize (locize.com/blog/i18n-pluralization)
- MUST always define the `other` plural case - it is the only category guaranteed to exist in every CLDR locale (locize.com/blog/i18n-pluralization)
- MUST format every date, number and currency value through `Intl.DateTimeFormat`, `Intl.NumberFormat` (with `style: 'currency'`) or `Intl.RelativeTimeFormat`, never a hand-built format string, so locale-specific separators, calendars and symbol placement come from the platform (consistent with next-intl's and i18next's own formatters, which wrap these same `Intl` APIs)
- MUST NOT put HTML/markup inside a translation string; use a rich-text component (`t.rich()` in next-intl, `<Trans>` in react-i18next) so tags come from code and only text nodes are translated (next-intl and react-i18next component docs)
- SHOULD namespace translation keys by feature/screen with nested or dot-notation keys (e.g. `checkout.errors.cardDeclined`) rather than one flat global namespace, so an unused or colliding key traces to its owner (i18next/next-intl namespacing convention)
- MUST negotiate the initial locale from `Accept-Language` (or a per-store declared locale) before falling back to a cookie or stored preference, and re-validate that preference rather than trusting a stale cookie forever (i18next/next-intl locale-detection middleware pattern)
- SHOULD match `Accept-Language` with a "best fit" matcher (`@formatjs/intl-localematcher`), not strict lookup, so a close variant (`en-GB`) resolves to a supported locale (`en-US`) instead of falling straight to the app default (next-intl.dev/docs/routing/middleware)
- MUST end every locale fallback chain on English, never on a specific non-English language picked because it was the first customer's language - a chain ending on, say, French silently serves French to every locale the platform has no translation for (general 2025-2026 i18n practice)
- SHOULD prepare for RTL from the start with CSS logical properties (`margin-inline-start`, `padding-inline-end`, `inset-inline-start`) instead of physical `left`/`right`, and set `dir` once on a container so one stylesheet serves LTR and RTL (developer.mozilla.org/docs/Web/CSS/margin-inline; modern-css.com/direction-aware-layouts-without-left-and-right)
- SHOULD use Tailwind CSS v4.2's built-in logical-property utilities (`ms-*`/`me-*`/`ps-*`/`pe-*`) for spacing and inset instead of physical `ml-*`/`mr-*`, which removes the need for a separate RTL plugin (tailkits.com/blog/tailwind-rtl-not-working)
- SHOULD run a translation-completeness check in CI that fails when a locale file is missing a key another locale has, rather than discovering the gap in production as a raw key or a wrong fallback - `i18next-cli status`/`extract --ci` or an equivalent key-diff tool is the concrete instrument, not manual review (i18next.com/how-to/extracting-translations)
- SHOULD lint for hardcoded literal JSX text (`react/jsx-no-literals`, or `eslint-plugin-i18next`'s `no-literal-string`) so a raw string cannot ship without going through the translation function (github.com/edvardchen/eslint-plugin-i18next)

## Topic 7 - PWA

- MUST declare `name`, `icons` (at least one 512x512, plus a maskable-purpose icon for adaptive platform shapes), `start_url` and `display` (`standalone` for an app-like PWA) in the manifest - installability is computed from these (web.dev/learn/pwa/web-app-manifest)
- SHOULD keep `short_name` under about 12 characters for constrained launcher labels, and set `theme_color`/`background_color` so OS chrome and the pre-stylesheet paint match the app (web.dev/learn/pwa/web-app-manifest)
- SHOULD set the manifest `id` field explicitly (e.g. `"/"`) so the browser keeps matching the installed app to its origin identity across future manifest edits, and keep the maskable icon's artwork inside a safe zone equal to a centered circle at 40% of the icon's width so adaptive-icon platforms do not crop the logo (web.dev/learn/pwa/web-app-manifest)
- MUST still register a service worker with a fetch handler for Chrome's own install-promotion gating even though Lighthouse's installability audit dropped its explicit "has a service worker" check in Lighthouse 11 (2023) - the two are not the same signal, and Lighthouse has also removed its dedicated PWA category entirely, so verify installability against Chrome's own installability documentation and DevTools, not a Lighthouse PWA score (developer.chrome.com/docs/lighthouse/pwa/installable-manifest; developer.chrome.com/blog/lighthouse-11-0; github.com/GoogleChrome/lighthouse/issues/15535)
- SHOULD expect Chrome's automatic install prompt (`beforeinstallprompt`) to be additionally gated by engagement heuristics (at least one interaction and around 30 seconds on page), not manifest validity alone, and capture the event to drive a custom install button rather than relying only on the browser's own UI (web.dev/learn/pwa/installation-prompt)
- MUST use network-first (or stale-while-revalidate with a short TTL) for navigation/HTML requests so a user online is never served a stale app shell (developer.chrome.com/docs/workbox/caching-strategies-overview)
- SHOULD use cache-first for content-hashed, versioned static assets (`main.[hash].js`) - the filename changes when the content does, so a network round-trip is pure waste (developer.chrome.com/docs/workbox/caching-strategies-overview)
- SHOULD use stale-while-revalidate for non-critical, frequently reused assets (avatars, fonts, non-critical JSON) that can tolerate being one version behind for a moment (developer.chrome.com/docs/workbox/caching-strategies-overview)
- MUST NOT cache API responses that reflect live or money-sensitive state, and MUST NOT intercept WebSocket/SSE connections in the service worker (developer.chrome.com/docs/workbox/caching-strategies-overview)
- MUST version caches by build and delete old-build caches in `activate`, so an update actually replaces what was cached instead of accumulating orphaned cache versions (developer.chrome.com/docs/workbox/caching-strategies-overview)
- SHOULD still use Workbox (v7) for non-trivial caching logic in 2026 - it remains the most widely used service-worker abstraction and integrates with Next.js/Vite build pipelines, rather than hand-rolling `Cache`/`fetch` event logic (web.dev/learn/pwa/workbox; getfishtank.com/insights/building-native-like-offline-experience-in-nextjs-pwas)
- MUST treat `Notification.permission === 'granted'` and an actual push subscription as two different facts - permission is consent to show notifications, `PushManager.subscribe()` (with the VAPID public key) is what produces the endpoint/keys a server can push to; a flow that stops after requesting permission never delivers anything (medium.com/bawilabs/web-push-notifications-through-vapid-method; developer.mozilla.org/docs/Web/API/PushManager/subscribe)
- MUST send the subscription's endpoint and keys to the server immediately after `subscribe()` succeeds and store them keyed to the user/device - the subscription, not the permission flag, is what the server needs (medium.com/bawilabs/web-push-notifications-through-vapid-method)
- MUST sign every push request with a VAPID JWT per RFC 8292 (ES256, `aud`, `exp` <= 24h, `sub` as a mailto/contact URI) matching the key pair used at `subscribe()` time, and treat the pair as generate-once, never-rotate infrastructure - rotating VAPID keys silently invalidates every existing `PushSubscription` with no error surfaced anywhere, so notifications simply stop arriving (developer.mozilla.org/docs/Web/API/PushSubscription; blog.mozilla.org/services/2016/08/23/sending-vapid-identified-webpush-notifications-via-mozillas-push-service)
- SHOULD treat the service worker's `pushsubscriptionchange` event and a `410 Gone` response from the push service as the signal that a subscription has expired and must be re-created, not as an error to retry against the same endpoint (developer.mozilla.org/docs/Web/API/PushSubscription)
- SHOULD audit service-worker caching with the Chrome DevTools Application panel (cache storage inspection, the "Update on reload" toggle) in addition to any automated check, since real update behavior can differ from a dev-mode-forced reload (developer.chrome.com Application panel documentation, per current 2026 PWA testing practice)

## Conflicts and gaps versus ENGINEERING_STANDARD.md

### (a) Practices the standard contradicts

- Barrel files: CODE.5 permits "barrel `index` files" as long as they "only re-export." 2025-2026 tooling guidance (Vercel's own Next.js engineering blog, bulletproof-react, and reported 2026 Turbopack build-memory costs) treats even a pure re-export barrel as a tree-shaking and build-memory hazard in a Next.js/Turbopack or Vite app - the cost comes from the bundler having to keep every re-exported module live, not from the barrel containing logic. CODE.5 should be narrowed: barrels only for small, leaf-level, side-effect-free groups; anything larger, or crossing a client/server boundary, should import directly or go through `optimizePackageImports`.
- "No per-component stylesheet" vs `styled()`: UI.1's "no per-component stylesheet" reads as a flat ban, but MUI's own recommended pattern for reusable styling is `styled()` - CSS-in-JS that is, by construction, scoped to and injected per component. For a MUI-based repository this rule needs an explicit carve-out distinguishing the actual defect (ad hoc, scattered, non-tokenized CSS files or duplicated inline styles) from a co-located, theme-driven `styled()` component, or the rule as written bans the framework's own best practice.

### (b) Practices the standard lacks and should add

- Name the actual new WCAG 2.2 criteria under A11Y.1 (2.4.11 Focus Not Obscured, 2.5.7 Dragging Movements, 2.5.8 Target Size at 24x24 CSS px, 3.3.7 Redundant Entry, 3.3.8 Accessible Authentication (Minimum)) instead of the current unqualified "44px touch targets" and "contrast 4.5:1" - 3.3.8 is directly relevant given TOTP/MFA flows (paste and autofill must work).
- Split the single "contrast 4.5:1" line into the two real thresholds: 4.5:1 for normal text (1.4.3) and 3:1 for large text and non-text UI components such as borders/icons/focus rings (1.4.11).
- Add a named European Accessibility Act rule: enforceable from 28 June 2025 for any e-commerce service sold to EU consumers; explicitly state a storefront is squarely in scope while an admin-only console has disputed scope in current legal guidance, so it must not be assumed exempt. A11Y.1 currently says only "a legal expectation" with no regulation named, and EAA also carries practical MUSTs beyond WCAG parity (a public accessibility statement per product/service, a defined complaint procedure) that are not in the standard today.
- Add `prefers-reduced-motion` handling to A11Y.1 - currently absent entirely.
- Add a stable-keys rule to the Code rules (never array index as a React key unless the list is provably static) - this exists only at one repository's own CLAUDE.md level today, not in the shared standard, despite being a generic, stack-relevant React footgun.
- Add React 19 compiler memoization guidance: stop reaching for `useMemo`/`useCallback`/`React.memo` by default; the two real exceptions are code inside `try/catch` and libraries that depend on referential equality. Prevents both "over-memoized" and "under-memoized" review disputes on any repo running React 19.
- Add an ICU/CLDR plural rule to I18N.1: forbid a naive `count === 1 ? x : y` ternary and require ICU MessageFormat plural branches with a mandatory `other` case. The standard already requires "no markup in catalogue value" and complete locale keys, but says nothing about plural correctness, a distinct and common defect class in a genuinely multi-language platform.
- Add RTL readiness to I18N.2 (CSS logical properties, a single `dir`-driven stylesheet) - the English-floor fallback rule says nothing about layout direction, and a platform that accepts "any ISO 639-1 code" will eventually serve an RTL language.
- Promote the Web Push permission-vs-subscription distinction, and the silent-breakage-on-VAPID-key-rotation lesson, into PWA.1 itself and into the §8 lessons catalogue. Both are currently recorded only in one repository's own CLAUDE.md ("nothing reports an error" on rotation) - exactly the kind of hard-won, cross-stack-relevant, silently-failing lesson the standard's own §9 promotion rule ("updated when the third repository makes the same deviation") and P.1 ("a guard nobody has watched fail") exist to absorb, and it is confirmed as a universal MDN-documented API behavior, not an ecomm-specific quirk.
- Add mobile viewport-unit guidance (`100svh` vs `100dvh`, and never animating toward `100dvh`) to UI.1/PWA.1 for any phone-first surface - currently unaddressed, and adjacent to but distinct from the "never serve a stale shell" lesson PWA.1 already encodes.
- Note in PWA.1 (or its rationale) that Lighthouse's PWA category and installability audit have been removed/changed as of the current criteria, so any future PWA gate should target Chrome's installability documentation directly rather than a Lighthouse PWA score that no longer exists in its old form.
