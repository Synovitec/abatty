# i18n rules (loaded when a locale file or a component is open)

Depth and reasons: `ops-hub/engineering/guides/I18N.md`.

- No literal user-facing text in JSX; everything goes through the i18n layer
  (`react/jsx-no-literals` or `eslint-plugin-i18next` at error).
- Keys are semantic and namespaced by feature or domain, 2 to 3 levels deep
  (`invoices.form.dueDate.label`), one casing decided once. Never named after the text.
- One key per UI instance: identical text is not identical meaning. `common` holds only what is
  universal and stable (months, countries, a dialog's "Cancel") and stays under a few hundred
  keys.
- Adding a key means adding it to every locale in the same commit; the pre-commit hook refuses
  a partial set and CI fails on a key one locale has and another lacks. The default language
  is the master; the others derive from it.
- Plurals are ICU MessageFormat with an `other` case, never a `count === 1` ternary. Interpolate
  only runtime values; when the possible values are known, write complete sentences.
- No HTML in a translation value: `t.rich()` / `<Trans>` with the tags supplied by code.
- Dates, numbers and currency through `Intl` (the library's formatter), never hand-built. No
  country or language list in code: `Intl.DisplayNames` and ISO tables.
- Server-side messages return an error `code` plus params; the client translates.
- No fallback chain ends on a specific non-English language; English is the floor. A missing
  key shows the master language, never the raw key.
- `lang` and `dir` set on `<html>` from the locale; layout uses logical properties
  (`ms-*`, `pe-*`, `inset-inline-start`) so an RTL locale needs no second stylesheet.
- Unused keys are audited on a schedule (`i18n-unused`, `i18next-parser`).
